# Exam Scheduling and Room Allocation System

A Python, SQLite, and Streamlit application for generating and reviewing exam schedules using synthetic academic data.

> **Data notice:** This project uses synthetic demonstration data. It is not intended to schedule real institutional examinations without further policy, security, and operational validation.

## Overview

The system models students, courses, enrollments, exams, exam requirements, rooms, room capacities, invigilators, availability, accommodations, and schedule assignments. It generates a reproducible dataset, applies scheduling rules, reports exams that cannot be scheduled, records scheduling events, and presents results in a Streamlit dashboard.

## Main capabilities

- Deterministic synthetic data generation using seed `20261022`.
- Configurable dataset size; default scale is 5,000 students, 300 exams, 100 rooms, and 200 invigilators.
- SQLite schema with primary keys, foreign keys, uniqueness constraints, and validation checks.
- Exam/room scheduling that considers student conflicts, room capacity and availability, exam duration, accessibility/equipment requirements, and invigilator availability.
- Reason-coded unscheduled exams.
- Scheduling event history for traceability.
- Streamlit views for the overview, schedule, unscheduled exams, audit history, and data overview.
- CSV, JSON, and SQL exports, plus data dictionary and ground-truth scenarios.
- Tools for validation, export verification, and reproducibility checks.

## Run locally (Windows)

Open Command Prompt or the VS Code terminal in the project directory.

### 1. Create and activate a virtual environment

```cmd
python -m venv .venv
.venv\Scripts\activate
```

### 2. Install dependencies

```cmd
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

### 3. Generate the synthetic database

The generator uses seed `20261022` and the default record counts listed above.

```cmd
python generate_data.py
```

**Warning:** the generator can replace its configured output database. Back up any database you need to keep before running it. Do not point it at a database containing work you want to preserve.

### 4. Select the database

For a root-level database generated by the command above:

```cmd
set "EXAM_SCHEDULING_DB=%CD%\generated_exam_scheduling.db"
```

The environment variable is specific to the current terminal session. `app.py` and `database.py` use it when set; otherwise, the application defaults to `generated_exam_scheduling.db` in the project directory.

### 5. Run the scheduler and validator

```cmd
python scheduler.py
python validator.py
```

Review `validation_report.json`. Do not rely on the schedule unless validation passes and unscheduled exams have appropriate reason codes.

### 6. Run automated tests

```cmd
python -m unittest discover -s tests -v
```

### 7. Launch the dashboard

```cmd
python -m streamlit run app.py
```

Open the local URL printed in the terminal, normally `http://localhost:8501`.

### 8. Export and verify data

```cmd
python export_data.py
python verify_exports.py
```

Exports are written to `exports/`. Review the generated manifest and checksums.

### 9. Check reproducibility

Use a separate output path so the reference database is not overwritten:

```cmd
python generate_data.py --output reproducibility_test.db --seed 20261022
python check_reproducibility.py
```

Confirm the exact arguments supported by the scripts with `python generate_data.py --help` and `python check_reproducibility.py --help` if your local version differs. Keep temporary comparison databases out of the submission.

## Ground-truth / negative scenarios

The project documents expected rejection cases for:

1. Two exams with a shared student being assigned to the same time slot.
2. Assigning an exam to a room with insufficient capacity.
3. Assigning one invigilator to overlapping exams.
4. Ignoring an accessibility or extra-time accommodation.
5. Assigning an exam to a room during an unavailable slot.

Ground truth is for evaluation and should remain separate from operational input features. A scenario's presence in a ground-truth file does not, by itself, prove that the scheduler rejects it; verify that behavior with tests.

## Reported run (verify against the submitted commit)

A previously tested local run reported 300 non-cancelled exams, 292 active assignments, 8 unscheduled exams, zero validation errors, and zero warnings. These are historical results, not a guarantee for every database or future code version. Re-run the scheduler, validator, and tests on the exact commit you submit.

## Data model and integrity

The schema and generated data are intended to maintain relationships between parent and dependent records. Before submission, check:

- Primary-key uniqueness and foreign-key integrity.
- Allowed values, dates, lifecycle states, and duplicate rules.
- That assignment totals reconcile with active, cancelled, and unscheduled states.
- That every unscheduled exam has a reason.
- That room capacity, availability, student-conflict, accommodation, and invigilator rules are enforced.
- That schedule changes are traceable through event records.
- That ground truth is not used as an operational scheduling input.

## Deployment

The Streamlit deployment should point to the intended database file and use the same code version as this repository. For Streamlit Community Cloud, select this repository, the intended branch, and `app.py` as the main file. Install dependencies from `requirements.txt`.

If the app requires a non-default database path, configure `EXAM_SCHEDULING_DB` in the deployment environment. Ensure that the selected database file is included in the repository or created by a documented startup process. Do not assume that a local environment variable is automatically present in the cloud deployment.

**New deployment URL:** add the verified URL here after deployment.

## Limitations

- Data is synthetic and intended for a coding challenge/demo.
- Scheduling quality and correctness depend on the implemented constraints and validation coverage.
- A passing validator only demonstrates that the implemented checks passed; it does not prove every possible edge case or institutional policy is covered.
- Before real use, add institution-specific policy review, security/access controls, backup/recovery procedures, and broader testing.
